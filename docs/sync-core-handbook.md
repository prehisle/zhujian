> 目标是让一个没跟过演进史的人,在一天内建立起正确的心智模型,并且**在改坏东西之前知道自己正在改坏东西**。

>
> **范围**:同步数据层(oplog / 回放 / 收敛)、传输与加密、配对与引导、纪元与隔离、备份恢复的**语义**。不含 UI、不含纯本地功能。

## 1. 十分钟心智模型

### 1.1 一句话

**本地优先的 op 日志复制**:每台设备把自己的每一笔写记进本地 `oplog`,加密后经零知识中转服务器广播给同账户的其他设备;对端把 op 按序**回放**进自己的库。没有中央权威副本 —— 每台设备的库都是全量,服务器只是接力员,**真相在设备日志的并集里**。

### 1.2 角色

| 角色 | 是什么 | 关键事实 |
|---|---|---|
| **账户**(account_id,ULID) | 一组互相同步的设备 = 一个同步域 | 客户端创号那刻自生成;服务器对 fresh 账户直接 TOFU 建档(无邀请码) |
| **空间** | 账户的客户端投影:**空间 = 账户 = 独立的 SQLite 库** | 一台设备可装配多个空间,各空间独立 transport、互不相扰 |
| **设备**(device_id,ULID) | `sync_meta.device_id`,触发器冻结 | **库即身份**:库丢了 device_id 即新;旧 id 成幽灵 origin(各端日志里它的 op 仍是史实,水位定格,无害) |
| **服务器**(`zhujian-syncd`) | 零知识中转 + 信箱 + 配对桥 + 引导直通 | 唯一持久化 = registry(账户→设备→公钥)+ 封禁表;**永不落**帧内容、信箱、密钥。服务器上没有不可再生数据 |

### 1.3 密钥体系(三把钥,别混)

| 钥 | 是什么 | 丢了会怎样 |
|---|---|---|
| **K_acc**(账户主密钥) | 32B CSPRNG,创号首台生成;只以一种形态离开本机:配对会话密文(曾有「恢复码」人眼形态 + 创号抄写仪式,用户面 125 起拆掉;加密备份文件里也带它,钥是备份码) | 所有设备全丢 + 没有备份文件 = **谁也救不了**(零知识的证明) |
| **设备鉴权钥**(Ed25519) | 入账户时生成,公钥进服务器 registry;只管「服务器认不认你」 | 与数据加密无关;吊销即断中转腿 |
| **备份码**(backup-plan §5) | `.zjbak` 加密备份文件的钥,**每台设备各自一把**,与 K_acc 无关 | A 的备份码解不开 B 做的备份;不做备份就不需要它 |

数据加密:`HKDF-SHA256(K_acc, "zhujian/sync/v1/" + domain)` 派生**域子钥**(`op` / `ctl` / `boot` / `blob` 四域),XChaCha20-Poly1305,AAD 绑 `[ver, account, from, to, domain]` 且**逐字节**(CBOR preferred serialization)。跨账户/跨设备/跨域拼接必解密失败。

**诚实边界**:K_acc 与设备私钥**明文存本机** `sync_meta` —— 本地库本就明文存全部笔记,给密钥加壳不给数据加壳是安全剧场;本机磁盘不在威胁模型内(sync-protocol §11)。

### 1.4 数据面:一张 oplog,三根轴

每笔写在业务表落地的**同一个事务**里发一条 op 进 `oplog`。op 的三根轴**并存不互代**:

| 轴 | 是什么 | 用途 |
|---|---|---|
| `op_id`(ULID) | op 的**身份** | 幂等判重的入口(判重本体是六字段完整比对,见 §2-4) |
| `hlc`(混合逻辑钟,尾缀 device_id) | **合并排序轴** | LWW 谁赢谁输看它;per-origin 内严格单调 |
| `origin_seq` | **传输与水位轴**:每设备给自己发射的 op 编连续号 1..n | 缺口可检、可等、可补 —— 没有它,信箱丢帧就是无声的数据丢失 |

**词汇表**(oplog 的 entity×kind CHECK,当前形在最新那条重建 oplog 的迁移里):

- `item` / `topic` × `create` / `set_field` / `tombstone`
- `link` × `link_add` / `link_remove`(OR-set,**刻意无墓碑**)
- `image` × `image_add` / `image_tombstone`(图只增删不改)
- `space` × `set_field`(空间名:单例 LWW 寄存器,entity_id 恒 `'profile'`,无 create)
- `device` × `set_field`(设备别名:多实例寄存器,entity_id = device_id)
- `comment` × `create` / `tombstone`(**刻意无 set_field** —— 留言不可编辑,改错删了重写)
- `board_column` × `create` / `set_field`(白名单只有 `title` | `position`)/ `tombstone`(六个种子列**不发 create**)

**收敛模型**:字段级 LWW(HLC 大者胜)+ link 的 OR-set(remove 只覆盖它 observe 过的 add)+ tombstone-sticky(墓碑后的迟到写一律压制)。全部按**日志全集重算**,与到达序无关 —— 这是「乱序但最终全到 ⇒ 终局一致」的根据。

### 1.5 一次同步会话怎么走

```
连接 WSS ──challenge/auth(Ed25519 签名,域隔离前缀)──> authed
   │
   ├─ 广播 hello{水位向量: origin → 本机连续最大 seq}     (ctl 域,mail lane)
   ├─ 收对方 hello:对每个「我高你低」的 origin 回 ops 帧   (任何持有者都能补任何 origin)
   ├─ 实时:本地新 op → 加密 ops 帧 send{to:"*"};ack 才推进 last_pushed
   └─ 收端引擎(sans-io):解密 → 帧级硬校验 → pending 池按 origin 分队
        仅当队头 seq == watermark+1 才出队 → replay::apply_remote_op(每 op 一事务)
```

- **两条 lane**:`mail`(离线入信箱;op/ctl 控制帧)/ `direct`(仅在线;boot/blob 大流量)。信箱有 TTL 与容量、重启即失 —— **丢帧不是丢数据**,水位互补自愈。
- **图字节旁路**(blob 域):`image_add` op 应用后行不建,字节按需拉流(`blob_want` 广播 → 谁有谁答 → 256 KiB 分块,块大小是**合规判据**);全到验 hash 才建行。
- **追赶不要求同时在线**:hello/ops 都能躺信箱,TTL 内接力;超时下次 hello 兜底。

### 1.6 新设备怎么进来(配对 + 引导)

1. **配对**:老端开槽得 9 位槽号,配对码 = `slot-SECRET`;双方以 SECRET 跑 **SPAKE2**(服务器盲桥透传,MITM 只有一次在线猜测,失败烧槽)→ 会话密钥下老端交 `{account_id, K_acc, server_url}`,新端交 `{device_id, pubkey}` → 老端 `register_device` 背书注册。
2. **引导**(bootstrap):新端自证 **fresh-to-account**(两条判据缺一不可,§2-9)→ 老端 `VACUUM INTO` 一致性快照 → boot 域直通流式 → 新端 ATTACH 只读、**回放豁免单事务**表级导入(含 oplog 原样)→ 导入后全量**审计**(op 形态双序 / 墓碑复活 / **op-backed 语义重算比对终态**,不符整体回滚)→ 水位一次抬到位,与实时流无缝续上。
   - 为什么不能靠 op 回放建库:同步纪元之前的存量数据没有 create op(legacy 随快照走)。

### 1.7 局域网直连(L 系列)

**中转恒为主路,直连只是加速层**:Hello 捎带通告、三步双向握手、来路亲和 + 路由健康表。内容机密性不弱于经恶意中转;新增的是**元数据面**(同网旁观者可见设备 ULID 与拓扑)。规格在 lan-direct-plan(内部文档),对被移除设备的直连闸见 §4-4。

## 2. 不变量清单

> 每条:**它说什么 / 破了什么后果 / 谁在守**。改动碰到任何一条,先读 §5。

1. **oplog append-only**。op 一旦落库永不 UPDATE/DELETE(触发器 `trg_oplog_immutable` / `trg_oplog_no_delete`;纪元压实是唯一例外,走受控整本重写,§4-5)。破了 = 各端日志集不再可比,收敛无从谈起。

2. **per-origin `origin_seq` 连续 1..n 无洞,且 seq 序 == HLC 序**。发射侧靠「进程内单写者(`write_locks` 全局互斥)+ 取号与数据写同事务」保证,`UNIQUE(origin, origin_seq)` 是响亮兜底不是机制。破了 = 水位协议失去地基。

3. **水位 = `MAX(origin_seq)` 派生,不存**;收端**只应用 `watermark+1`**,水位永不越过缺口。这是整个引擎的正确性支点:挂起 op 只存内存、崩溃即丢**无害** —— 水位没过它,重连后任何持有者按 hello 重喂。**任何「跳过一条往前走」的改动都在动这条命根**。

4. **判重 = 六字段完整比对**(hlc/entity/entity_id/kind/payload/origin_seq),不是只比 op_id。同 op_id 异内容被当重传吞掉 = 两端水位都齐、hello/want 永不再修的**静默分叉**。同坐标不同内容 = 分叉,冻结该 origin(§3)。

5. **op 与 origin 的绑定不可破**:帧内全部 op 的 HLC 尾缀必须 == 帧 `origin`(入池前硬校验,整帧拒收)。帧 origin 允许 ≠ 发送者(代补是设计),但标错 origin 会把水位推过不存在的号 → 真 op 到达被当已见丢弃,**不可自愈**。

6. **device_id 冻结,库即身份**。服务器拒任何「device_id 已在 registry 且公钥不同」的注册 —— 把「整库拷贝当第二台」从灾难性 HLC 撞车降级为一次响亮的配对失败。⛔ 想给两台机器「拷库省事」= 同 device_id 两写者 = 真分叉,正道是「加入空间」重新引导。

7. **AAD 逐字节即协议**(CBOR preferred serialization,definite-length、最短前缀);内层消息扩展**优先走 `RemoteOp.kind`/payload**,新增顶层变体 = 协议破坏必须升 `PROTO_VER`。理由:kind 级偏斜落 `UnsupportedVocab` 可挂起自愈,顶层变体偏斜只能整帧 `Codec` 响亮卡住(§3)。

8. **`born_device` / `born_stage` 不可从 oplog 派生**。纪元压实会整本重写 origin(identity-plan §3.1)—— 「谁创建的」这类史实必须落表列并由触发器冻结,不许「要用时从日志算」。加同步字段前先问「压实后它还算得出来吗」。

9. **fresh-to-account 两条判据缺一不可**(引导准入):(a) 本地无他人 origin 的 op、无既往引导记录;(b) 本地现存全部实体都有本机 op 背书。少了 (b),legacy 无背书行永远不进水位视野 —— 全网只此一份还自以为同步了。legacy 只允许存在于账户首台(快照源)。

10. **迁移不许回填同步字段**(表有值、op 无 → 跨端分叉);存量修复走**开库自愈**(检测到缺口时按正常发射路径补 op)。纯本地表(不发 op 不进同步)不受此限,迁移回填反而是义务(如已读水位归全已读)。

11. **图不可变**:图只增删不改(禁 UPDATE 触发器)、「图N」编号高水位**永不复用**(删图留洞不重排)、正文「见图N」引用永不静默改指。撞号由 HLC 大者顺延并**提示用户**(翻案义务)。

12. **删除语义分层**:tombstone 是 sticky 的(delete-wins:墓碑后一切迟到写压制);`link` 的删除是 OR-set 的 `link_remove`(只覆盖 observe 过的 add,**没有墓碑**);`item_revisions` 由本地触发器归档,**原文永不被覆盖而不留历史**(563/0039 起有且只有一个例外:一次编辑只有方框里那一个字符翻了 = 勾选,不记那一版;判据在 `core/src/checklist.rs`,见 design-rules 同条)。

13. **服务器 registry 是权限的唯一执行点**。E2EE 下同步数据里的任何「权限记录」都是人人可写的 LWW 装饰 —— 管理设备、席位、封禁全部落在服务器侧。反过来:**服务器改不了内容**(AEAD+AAD),它能做的只有拒绝服务、丢帧(水位自愈)、重放(op_id 幂等吸收)。

14. **恢复恒产出新空间,绝不覆盖**(backup-plan §16.2)。覆盖是不可逆销毁,且会当场触发 `NativeFileKey` 与读租约两条休眠账的门。任何人想加「原位恢复/覆盖/同名重建」路径,先去读那两条门(backlog 休眠账,内部文档)。

15. **`CORE_TABLES` 是 catalog 的准入判据**:在册的表缺一即**拒开库**。⛔ **名单只认 `core/src/spaces.rs` 那一份**(后来加的那几张旁边各写着自己为什么在册),别在这儿抄第二份 —— 抄了就会腐烂,552 草稿那份到 596 就已经少了一张。**在册的是两类**:①op-backed 正表(items / topics / oplog / item_comment / board_column …);②**触发器依赖的回放标志表**(`sync_replay_active`、`item_checklist_toggle` 这种单行表)—— 它们不发 op,但写保护触发器的 `WHEN` 要查它们,**缺了第一笔业务写就炸**,所以同样在 catalog 这一层就拒、不许拖到写入时。**不在册的是纯本地可重建的**:`item_image_thumb`(派生缓存,整表可删下次自动补)、`item_comment_seen`(用户状态,重建不出 —— 迁移与引导导入尾把它保守回填成全已读)、`sync_quarantine`(设备本地隔离档案)。**分清一张新表落哪一类,是加表时的第一问**(§5.2)。

16. **混版是硬约束,闸放发送端**。旧端遇到不认识的东西,最好的归宿是 `UnsupportedVocab`(挂起,升级即自愈);最坏的归宿是 `InvalidOp`(**per-origin 持久隔离** + 后续帧到即丢)。所以:新能力若会让旧端把**合法** op 判成 InvalidOp,必须在**发送端**加能力闸(全员就绪才开写),服务器帮不上忙 —— 它读不懂密文。判例:自定义看板列(board-columns-plan,内部文档)。

## 3. 错误分型与自愈路径

> 回放层的分型在源头(`replay.rs` 的 `OpError`,typed 枚举,不靠错误字符串事后分类);
> 引擎按型分道。**改了形状校验的判定规则,必须 bump `replay.rs` 的 `VALIDATOR_VER`**(§5.4)。

### 3.1 四型 + 三种引擎级处置

| 型 / 态 | 什么触发 | 引擎处置 | 自愈路径 |
|---|---|---|---|
| **`UnsupportedVocab`** | 词汇表外的 entity/kind/field = **版本偏斜**(对端更新) | 该 origin 内存挂起,水位不动;UI「对端版本较新,请升级」 | **升级即自愈**:新版重喂自然继续,零丢失 |
| **`DependencyMissing`** | 已知词汇、跨 origin 因果未到(父行缺失且无墓碑、列还没到) | 同上挂起;每有 op 落地对全部挂起头再试一轮到不动点 | 依赖到达即续;崩溃丢挂起无害(水位没过) |
| **`InvalidOp`** | 已知词汇下的**非法**:字段缺失/值域错/身份自相矛盾(shape 层),或重复 create 等状态型非法(apply 层) | **持久隔离**:`sync_quarantine` 记 per-origin 首个被拒 op 的完整 blob + 双坐标(origin / relay-from),**该 origin 后续帧到即丢**;UI 常驻告警 | 升级重验(§3.2)或人工处置(§4-2) |
| **`LocalFault`** | 本地 IO/SQL 故障,与 op 内容无关 | 原样冒泡,会话层处置;不隔起不挂起 | 修本地环境 |
| `AlreadySeen` | 重复帧(六字段完整相等) | 幂等吸收,推水位 | —(设计内噪音:多端同答 hello) |
| **分叉冻结**(frozen) | 同 (origin, seq) 不同内容 / 本机 origin 回声对账不符 / 跨帧双序矛盾 | **冻结该 origin 的同步** + UI 报错;冻结是内存态、重连重检 | 无自动路 —— 现实来源几乎总是「旧备份整库回滚复活旧身份」,走 §4-3 |
| **`Codec`**(顶层变体未知) | 对端用了本端不认识的**消息变体**(真·协议升级) | 整帧拒收挂不上 origin;水位不动、hello/want 反复重取 = **响亮卡住** | 升级本端 |

**判定顺序是规格**:入池的坐标/分叉检查**先于** shape 隔离 —— 伪造 self-origin 的畸形 op 必须先走「回声对账 → 冻结」,不许被 shape 层判 quarantine 掩盖身份问题。

**资源边界都是 fail-closed 的**:quarantine 行数/字节到顶、frozen origin 数超上限 → **poison-breaker** 落盘置位,引擎拒收未在册 origin 的帧,重启不忘;解除 = 人工处置后显式复位。宁停不吞。

### 3.2 升级重验状态机(误判的自助恢复路)

隔离行记着隔离时的 `validator_ver`。升级后引擎对 `validator_ver < VALIDATOR_VER` 的行以新规则重跑 `op_blob`:

- 仍 Invalid → 保留(真毒);
- 变 Unsupported → 转普通版本挂起;
- shape 已接受 → **清隔离、op 放回 pending、发 `want{watermark+1}`** 追回隔离期间丢掉的后续帧;
- 到 apply 位置仍状态型 Invalid → 以新 validator_ver 重新隔离。

这条路真兑现过一次:`stage` 值域从六值枚举放宽到「种子 ∪ 严格 ULID」那一跳(v7→v8),把旧规则误隔离的 origin 放了出来(此后归 DependencyMissing 挂起)。**所以 bump 纪律是硬的**:改了判定规则不 bump,升级救不出任何人。

### 3.3 混版行为速查(排障先查这张)

| 现象 | 多半是 | 去哪看 |
|---|---|---|
| 某台一直「追赶中」,提示「对端版本较新」 | kind/field 级偏斜(UnsupportedVocab) | 升级那台,自动续 |
| 状态里 skew、某 origin 水位卡住不动 | 顶层变体偏斜(Codec,整帧读不懂) | 升级本端 |
| UI 告警某 origin 被隔离 | InvalidOp(真毒 / 旧版规则误判) | §4-2 |
| UI 报某 origin 分叉冻结 | 旧备份回滚 / 整库拷贝 | §4-3 |
| 留言/新实体在旧端看不见、其他数据正常 | 旧端把那族 op 挂起了(正常偏斜) | 升级即可,挂起零丢失 |

## 4. 坏了怎么恢复(按症状索引)

> 原则:**分层递进,永远先试最轻的**。多数「坏了」是版本偏斜,升级就好;真正要动手的只有下面几种。
> 运维命令(ssh / admin 面 / 封禁表)全在 deploy.md(内部文档),这里只给语义与次序。

### 4-1 同步挂起 / 版本偏斜

**什么都不用修**。挂起是设计:水位没过缺口,升级慢的那端后重喂,零丢失。⛔ 别「帮忙」清库重配 —— 那才会把没同步出去的东西弄丢。

### 4-2 origin 被持久隔离(quarantine)

1. 看 UI 双坐标(origin + relay-from)。⛔ **不得断言 origin 设备 = 作恶发送者** —— 帧可能是别人代补的。
2. 两端都升到最新版,等升级重验(§3.2)自动裁决。
3. 重验仍 Invalid = 真毒(坏实现/恶意):**吊销该设备 + 它清库重配**。换新 device_id 后旧 origin 永不再现,隔离行成死档可清。
4. breaker 置位过的,处置完显式复位。

### 4-3 origin 分叉冻结

几乎总是「**旧备份整库回滚**」:复活的旧身份重用了已花掉的序号。协议**刻意不静默修复**(两边都自以为对)。处置 = 以某端为准:

1. 判定哪端的数据要保(通常是没回滚的那端);
2. 回滚那端**重置该空间**(清本机副本)→ 重新「加入空间」配对 + 严格引导;
3. 它被冻结期间本机写的、没同步出去的 op 会丢 —— 如实告知用户,别许诺救回。

预防写进备份文案:**回滚同步库后不要直接联网**。

### 4-4 踢设备(丢了 / 离职)

E2EE 下「踢人」三层,**各不一样**(identity-plan §5.1,话术之根):

| 层 | 能不能断 |
|---|---|
| 被踢设备本地已有的数据 | **断不掉**(它持 K_acc,能永久解密自己那份库) |
| 服务器中转腿 | 能断:吊销即鉴权拒 + kick + 清信箱 + 烧配对槽 |
| 局域网直连腿 | 幸存端**有权威名册**时能断;名册未知时 fail-open 断不掉 |

- 日常:用户面「移除设备」或 admin 面吊销即可(数据面闸)。
- **彻底断干净只有纪元切换**(§4-5)—— 换 K_acc,旧密文从此互不可解。团队离职场景要的就是它。
- 「移除了还能回来吗」:能,但必须清空间重配(新 device_id 新身份,拉全量快照);它被移除期间没同步出去的内容**没了**。所以移除前让它先在线同步完。

### 4-5 纪元切换(不可逆账本重写;runbook = deploy §9,内部文档)

用途:彻底隔离(踢干净)/ 账本压实。八步的**次序是安全性质,不可倒**:

冻结追平 + 文件级备份 → 预注册新锚点身份(两阶段崩溃安全)→ **吊销全部非锚点** → 吊销旧锚点 → **重启服务清全部信箱**(吊销后才清 —— 否则旧身份重连的帧还会投进新信箱)→ **然后才离线压实**(K_acc 轮换)→ 锚点新纪元上线 → 非锚点逐台重置重配。

- 压实前维护页强制逐项勾选(已备份/已吊销/已清箱),防跳步 —— 这个闸是被一次真实的次序倒置买来的,别拆。
- **旧纪元备份 = 死档**:身份已吊、K_acc 已换,恢复它是运营者显式的災备动作。

### 4-6 数据误删找回(备份恢复)

- 删除是 delete-wins-sticky:她删 → 墓碑同步 → 所有端都删。**能救的只有删除之前的那份备份**。
- 恢复(`.zjbak` + 备份码)**恒产出一个未配置的新空间**,绝不覆盖现有数据(§2-14)—— 恢复因此是可逆的、「试一下」级的动作。找回后想要的条目走跨空间移动。
- 服务器**不是备份**:信箱易失、registry 无内容。真正的丢失窗口只有一个 —— 某设备独有的 op 在它硬盘死掉前没同步出去。

### 4-7 账户级问题

- **创号半途孤儿**(「设备身份被占用」):服务器按 device 反查吊销孤儿注册,用户原库原样重试(重试自生成新账户 ULID)。客户端**不清库**。
- **账户吊光最后一台 = 空墓碑封存**:任何 device_id 都不能再自助 TOFU 重开(防被吊设备满血复活)。默认路径 = 签发新 account_id 重来(服务器上本就没有数据);确需同号是运营者显式操作。

### 4-8 服务器灾难与回滚红线

服务器无不可再生数据(registry 可从台账/备份重建,信箱本就易失)。但 **registry 文件与二进制是同一个安全状态**,已激活的回滚红线(deploy §2,内部文档):

- ⛔ **绝不许恢复部署前的 registry 备份** —— 会把之后合法发生的吊销一起撤销,**把已吊销的设备复活**。
- 回滚二进制只许走「受控降级」:停写 → 基于**当前**文件只摘新键(`admins` 等)→ 上旧版。
- 空墓碑红线同理:旧二进制会把 `{}` 当 fresh 重新放开 TOFU。

## 5. 改动纪律(动这里之前)

### 5.1 什么改动要过对抗审

**动线协议 / 加密 / 数据层(oplog、回放、收敛)/ 迁移 / 服务端准入** = 收口前送 codex 多轮对抗审(项目工作节奏规则 1)。这不是仪式:这几层的缺陷形态是**静默分叉 / 静默丢失**,测试全绿也照样带病 —— 历史上这几层的 H 级洞(fresh 判据不全、帧 origin 绑定缺校验、引导语义审计缺失、密钥崩溃窗)全是对抗审在测试全绿的代码上抓出来的。纯 UI/文案不用。

动这几层还要在写第一版**前**过一遍 first-draft-checklist.md(内部文档,族内判据逐条带判例)。

### 5.2 新增同步实体 / 同步字段

**这是全项目最贵的一件事**。完整落地面在 architecture.md「新增一个同步实体的落地面」四节(内部文档),这里只给骨架:

- **A. 十一个横切面有机器守**(`core/src/entity_registry.rs` 登记表,漏一格当场红):词汇表 CHECK / CORE_TABLES / 压实指纹 / 压实基线合成 / 引导导入 / 墓碑复活审计 / 无背书行审计 / 因果前提审计 / 收敛测指纹 / apply 分发臂 / shape 校验臂。
- **B. 登记表守不到的**:kind 级臂完整性、VALIDATOR_VER bump、跨空间随迁、两壳命令面、两端 UI、两份字典、测试资产。⇒ **每个新实体必须自带「每种 kind 的往返行为测」+ 收敛测覆盖计数** —— 这是 kind 级今天唯一的兜底。
- **C. 只加一个字段也散在十来处**,最容易漏的恰是「本端改了对端永远收不到」那一类(发声端、shape 接受、apply)。
- **判例背下来**:往既有 create payload 加键,**旧端会把 op 原样存进日志却丢掉值** ⇒ 同轮必须带一条「从日志恢复」的迁移。

新同步字段默认**单版直发**(不做两版 reader/writer 分发)—— 混版旧端的归宿必须是「挂起自愈」或「非破坏的未知」,先按 §2-16 想清楚旧端会把它判成哪一型。

### 5.3 协议扩展

- 优先走 `RemoteOp.kind` / payload(旧端 → UnsupportedVocab,自愈);
- 新顶层消息变体 = 升 `PROTO_VER`(旧端 → Codec 响亮卡);
- AAD、CBOR 字节形态、签名域前缀都是**逐字节协议**,黄金向量测试焊死 —— 改动必须过向量对拍;
- payload 业务整数必须是 CBOR integer 且在 i64 内,禁 float。

### 5.4 VALIDATOR_VER

改了 `validate_op_shape` / apply 层状态型校验的**判定规则**就 +1(`core/src/replay.rs`,常量旁的版本史注释同步写一行)。纪律是「改了就 bump」,不是「有人要救才 bump」—— 你不知道现网有没有被旧规则误隔离的 origin 在等这一跳。

### 5.5 迁移

- append-only 表(oplog)的结构改动走**整表重建**(触发器拆了重建);
- **已应用的迁移永不改**(改了 = 存量库与 fresh 库真分叉);
- 同步字段回填禁令与纯本地表例外见 §2-10;
- 库版本是 exact-match 准入:旧版从此打不开新库,**升库版本 = 事实上的强制升级**,发版说明要写人话。

### 5.6 测试的底线

- **三实例收敛 property test**(`core/src/sync/convergence.rs`)是数据层的宪法:随机命令流 × 乱序 × 分区 × 信箱溢出 × 服务器重启,终局逐行相等。新实体要进指纹面**并配覆盖计数**(空表恒相等 = 假绿)。
- **新防回归测试必做变异阴性对照**(把规则改坏,确认测试真红且红的理由对)—— 门禁失灵的方式是安静的绿。
- 反例种子固化为回归测试;反复出反例 = 合并规则回炉,**别带病开闸**。

### 5.7 心法(三条,来自付过学费的地方)

1. **fail-fast,不写静默兜底**。这一层的「兜底」几乎总是把响亮的错误变成静默分叉。宁可挂起、宁可拒收、宁可 breaker 停机。
2. **水位不越缺口是命根**(§2-3)。任何优化若要「先跳过这条」,答案是不行。
3. **想清楚旧端**。每笔协议面改动的第一问不是「新端怎么写」,是「旧端收到会判成哪一型、能不能自愈」(§3.3 那张表)。
